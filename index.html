[ 001 ] LLMs

      
Large Language Models

      
transformers trained on massive text to predict next tokens. probability distribution over vocabulary is everything. GPT, Claude, Gemini, Qwen — same core architecture, different scale, data and post-training.

      
transformersattentiontokensRLHF

      
Karpathy: Intro to LLMs ↗

    

    
      
[ 002 ] RAG

      
Retrieval-Augmented Generation

      
ground your LLM in real data at inference time. prevents hallucinations about domain knowledge. chunk → embed → store → retrieve → generate. that's the loop.

      
embeddingsvector dbsemantic searchchromadb

      
Original RAG paper — Lewis et al. ↗

    

    
      
[ 003 ] Agents

      
Agentic AI & Tool Use

      
LLMs that call tools, take actions, loop until goal met. the model decides what to call. langgraph makes this stateful. crewai adds roles and collaboration.

      
ReActtool callingplanningLangGraph

      
ReAct paper — Yao et al. ↗

    

    
      
[ 004 ] Embeddings

      
Vector Embeddings

      
semantic compression of text into high-dimensional vectors. similar meaning = similar direction. text-embedding-3-small or bge-large are your go-to. dimensions matter.

      
cosine simada-002bgeFAISS

      
OpenAI Embeddings Guide ↗

    

    
      
[ 005 ] Prompting

      
Prompt Engineering

      
system prompts, few-shot, CoT, XML tags for Claude, JSON mode, output constraints. controlling model behavior without touching weights. massively underrated. master this first.

[ 014 ] Use Case Design

    
How to approach any GenAI problem

    

      

        define the task
        what's the input? what's the output? what does "correct" mean? if you can't answer these, don't write a line of code yet.
      

      

        pick the pattern
        static data + Q&A → RAG. multi-step autonomous task → agent. domain tone/style → fine-tune. most things are RAG. don't overengineer.
      

      

        eval first
        write 20 test cases before you write any code. if you can't measure it, you can't ship it. this is the hardest discipline to build.
      

      

        start minimal
        one agent, one tool. add complexity only when evals break. the system that ships beats the system that's perfect.
      

    

    

      
pattern picker

      
answers live in your docsRAG

      
answers live in a databasetext-to-SQL + tools

      
fixed steps, known orderworkflow / chain

      
steps depend on what it findsagent

      
same decision, thousands of timesclassifier / Jev

      
needs a voice or format RAG can't fixfine-tune

[ 015 ] LLM Comparison — updated Sep 2026

    
Current model landscape

    

      

        Claude Fable 5.1 / Opus 5.5 / Sonnet 5.5 (Anthropic)
        best for enterprise
        
Sonnet 5.5 is the daily driver for doc analysis and agent loops. Opus 5.5 for hard reasoning and long agentic runs. Fable 5.1 is the new Mythos-class tier on top, with extra safety gating. Haiku 4.5 still the cheap router. what I build with at work.

      

      

        GPT-6 Astra / Sol / Luna (OpenAI)
        best ecosystem
        
Astra is the flagship (early Sep). Sol is the coding / complex-task workhorse, Luna the high-volume cheap tier (both Sep 22). the 6 series is priced at half of 5.6. Codex + Responses API is the agent story.

      

      

        Gemini 3.1 Pro / 3.8 Flash (Google)
        best context + speed
        
Pro hasn't moved since Feb (3.1), 3.5 Pro slipped and Gemini 4 is teased. the action is in Flash: 3.8 Flash (Sep) targets long-horizon coding, 3.5 Flash-Lite is the budget pick. 3.8 Live for realtime voice. free tier still generous.

      

      

        DeepSeek V4 / Kimi K3 / GLM-5.2 / Qwen 3.8 (open weights)
        open weights
        
DeepSeek V4 Flash + Pro (MIT, 1M ctx) for cheap reasoning. GLM-5.2 tops open coding benchmarks. Kimi K3 is the biggest open model out there. Qwen 3.8 27B runs on a laptop and punches way above its size. Llama 3.3 is retired from my stack.

      

      

        Jev (TypeSafe) — not an LLM
        decisions, not text
        
System One model: typed Choice / Score / yes-no answers with calibrated probabilities in ~100ms. stop burning frontier tokens on routing and classification. full breakdown in the jev section below.

      [ 016 ] The AI Bubble ↗
      
Hype vs Reality

      
an honest take from someone building in it

    

    

      

        
what's overvalued

        
GPT-4 wrappers with no moat. $100M valuations on 3-person teams with no proprietary data. "AI-powered" SaaS that's literally just a prompt + API call with a landing page.

      

      

        
what's actually real

        
companies with proprietary data + tight AI integration. the infra layer (Anthropic, OpenAI, Google). tooling. domain-specific apps with high switching costs and network effects.

      

      

        
where value actually sits

        
data flywheel + fine-tuned models + workflow integration. models are being commoditized fast. your moat is your data and your eval pipeline. build those.

      

    

  
















  
01.7 — new model class

  
Jev: the model that doesn't talk

  
TypeSafe's "System One" model, launched Sep 2026. it doesn't generate text. it answers typed questions with calibrated probabilities. think of it as a smart if statement for your agent graph.


  
  

    

      
// the one-line pitch

      
most of the LLM calls in an agent pipeline aren't generation. they're decisions: which branch, is this safe, how urgent, is the answer grounded. Jev does only that, and does it fast and cheap.

      
System 1 vs System 2 (Kahneman): fast intuitive judgement vs slow deliberate reasoning. Jev is the fast one. your frontier LLM stays the slow one.

    

    

      
~100mstypical latency
(70–500ms range)

      
$0.042per 1M input tokens
output is free

      
0off-schema answers
it can't hallucinate a type

      
64ktoken budget across
state + questions

    

  


  
  

    

      
Choice

      
pick one of N

      
labeled options with descriptions, up to 255. returns the pick, the full probability distribution and a confidence score.

      
→ which agent handles this? which department? which tool?

    

    

      
Score

      
place on a scale

      
ordered levels (2–10). returns a probability-weighted score plus confidence. combine several into composite rankings.

      
→ how frustrated is the user? how risky is this diff? how relevant is this chunk?

    

    

      
Noul

      
yes / no as a probability

      
a single 0–1 probability. no confidence field, you set the threshold. that's the point: your code owns the cut-off.

      
→ is a refund requested? is this command destructive? is the answer grounded?

    

  


  
  

    

      
jev_router.pypython · pip install typesafe-sdk


from typesafe_sdk import TypeSafeClient, Choice, Noul

client = TypeSafeClient()  # reads TYPESAFE_API_KEY

res = client.system_one(
    state=user_message,
    questions={
        "route": Choice(
            instructions="Which specialist should handle this?",
            criteria={
                "rag":    "Question answerable from our docs",
                "sql":    "Needs numbers from the database",
                "human":  "Complaint, legal, or account change",
            },
        ),
        "urgent": Noul(instructions="Does this need a reply today?"),
    },
)

route = res.answers["route"]
if route.confidence < 0.5:
    next_node = "human"        # unsure → escalate, don't guess
else:
    next_node = route.choice
urgent = res.answers["urgent"].noul > 0.7

      
ask every question you might need in one call. latency comes from the shared state, not the number of questions.

    


    

      
where it slots into a LangGraph pipeline

      

        user msg→
        Jev: route + urgency→
        RAG / SQL / human→
        Claude generates→
        Jev: grounded?→
        reply
      

      

        
routingconditional edges without a frontier call. cheapest win.

        
tool gatingclassify a tool call as read-only / reversible / destructive before it runs. LangChain ships an AutoModeMiddleware for this.

        
guardrailsemergency / self-harm / PII / prompt-injection flags on every turn, at a cost you can actually afford per message.

        
eval checks"is this claim supported by the context?" as a Noul. a fast pre-filter before LLM-as-judge.

        
bulk labelingclassify 100k tickets, reviews or papers for cents. TypeSafe's own demo labeled ~1k papers for $0.08.

        
re-rankingScore retrieved chunks for relevance before they hit the context window.

      

    

  


  
  

    

      
use it when

      
the answer is one of a known set of options. you make the same decision thousands of times. latency matters (voice, chat, agent loops). you want a probability you can threshold instead of a string you have to parse.

    

    

      
don't use it for

      
writing prose or code. math, counting, or extracting dates and numbers (do that in code). images, audio or video (text in only, for now). anything needing more than ~32k tokens of state. open-ended reasoning: that's still your LLM's job.

    

    

      
honest caveats

      
brand new (Sep 2026), closed weights, architecture not published. the "40–400x cheaper" numbers are TypeSafe's own benchmarks on their own workflows. run it against your golden set before ripping out a working classifier.

01.6 — use case breakdown

  
PE Due Diligence Automation

  
a client comes to you with a problem. walk through how to deconstruct any GenAI use case — what to build, what to skip, and why.


  
  

    
// real use case — why this example

    

      

        
why this use case

        
PE due diligence is the ideal GenAI use case — structured inputs (PDFs), structured outputs (fixed report template), bounded reasoning, measurable quality. if you understand how this pipeline was built, you can build any enterprise document workflow.

the business problem

      
PE analysts spend 40–60 hrs per deal manually reading CIM documents, pulling news, checking financials, and writing the same structured due diligence report. the output format never changes. the work is high-volume, repetitive, and rule-driven.

    

    

      
why GenAI fits here

      
the inputs are structured (PDFs, web data). the output is structured (a fixed report format). the reasoning is bounded — not open-ended creativity. there's domain knowledge that can be encoded. measurable quality. this is the sweet spot.

    

    

      
what we shipped

      
multi-agent system (Verdikt). supervisor routes to researcher, analyst, writer. full report in ~90 seconds. the same architecture applies to any consulting, legal, or financial document workflow.

    

  


  


    

      

        decision 01
        what pattern fits this use case?
        → multi-agent
        +
      

      

        

          

            
✗ fine-tune

            
fine-tuning gives you style, not capability. you can't fine-tune a model to browse the web or query a vector DB. it's the wrong tool for tasks that require live data access and multi-step reasoning.

          

          

            
~ RAG only

            
RAG handles "answer questions from documents" well. but this use case requires: search the web → pull the CIM → cross-reference financials → structure a report. RAG doesn't orchestrate across steps — it just retrieves. you need something that can plan.

          

          

            
✓ multi-agent with RAG inside

            
the task decomposes cleanly: research (web + docs) → analyse (financial reasoning, risk) → write (structured output). each step is a specialist with its own tools. RAG lives inside the researcher agent. the supervisor orchestrates the flow. LangGraph manages state across all of them.

          

        

        
rule: if a human would break the task into distinct phases with different skills — it's multi-agent. if it's one Q&A interaction over documents — RAG is enough.

      

    


    

      

        decision 02
        which model? cost vs quality tradeoff
        → depends on the context
        +
      

      

        

          

            
✗ one model for everything

            
using a frontier model for every step including simple routing and classification burns money and adds latency. a PE firm processing 50 deals/month can't afford $0.30 per report step multiplied across 200 LLM calls.

          

          

            
~ Claude for everything

            
Claude Sonnet is excellent for document analysis and structured output. but using it for classification routing and simple transformations is overkill. reserve heavyweight models for heavyweight tasks.

          

          

            
✓ tiered model selection

            
routing + classification → Jev (typed decisions, ~100ms, fractions of a cent) or Claude Haiku 4.5 / GPT-6 Luna. document analysis → Claude Sonnet 5.5. deep financial reasoning → Claude Opus 5.5 or GPT-6 Sol. dev/prototyping → DeepSeek V4 Flash / Qwen 3.8 locally. the right model for the right step.

          

        

        
rule: route cheap tasks to cheap models. only pay for reasoning power when the task actually needs reasoning.

      

    


    

      

        decision 03
        how do you handle the input documents?
        → docling + chromadb
        +
      

      

        

          

            
✗ pypdf + naive chunking

            
CIM documents have financial tables, section headers, and structured data. pypdf strips all of that and returns a flat blob of text. you lose 40% of the signal before the model even sees it. never use this for structured financial documents.

          

          

            
~ stuff everything in context

            
works with Gemini's 1M context window, but expensive and slow. also doesn't scale when each deal has 200 pages of attachments. retrieval is still better architecture than long-context stuffing for production workloads.

          

          

            
✓ Docling → chunk → ChromaDB

            
Docling preserves table structure, headings, and section hierarchy — critical for financials. semantic chunking at 512 tokens, 50 overlap. ChromaDB for local dev, pgvector or Qdrant for production scale. hybrid retrieval (BM25 + semantic) for best recall.

          

        

        
rule: if your documents have tables or structured sections, use structure-aware parsing. docling > everything else for financial and legal docs.

      

    


    

      

        decision 04
        how many agents and what architecture?
        → supervisor + 3 specialists
        +
      

      

        

          

            
✗ single agent, all tools

            
one agent with 8 tools, a massive prompt, and a multi-step task loses track of what it's doing. context gets bloated. the model starts confusing its own outputs. quality degrades hard past ~5k tokens in the agent loop.

          

          

            
✓ supervisor + 3 specialists

            
Researcher — Tavily web search + ChromaDB RAG. focused on finding information. 2 tools max.
Analyst — financial ratio calculation, risk scoring, competitive positioning. gets researcher's output as context.
Writer — takes analyst output, generates structured Pydantic report. no tools, pure generation.
The supervisor routes between them. each has a tight prompt and a clear job. output quality is dramatically better.

          

        

        
rule: specialisation beats generalisation in agents. a focused agent with 2 tools outperforms a god-agent with 10. decompose until each agent has one clear job.

      

    


    

      

        decision 05
        how do you measure if it's actually working?
        → structured output + RAGAS
        +
      

      

        

          

            
✗ vibe check / manual review

            
not scalable. when a PE analyst says "looks good", what exactly looks good? you have no baseline. you can't track regression. you don't know if a prompt change made things better or worse. subjective review is not an eval.

          

          

            
✓ pydantic schema + ragas metrics

            
Pydantic output model validates structure on every call — if the agent produces a malformed report, it fails immediately. RAGAS measures faithfulness (are claims grounded in source docs?), context precision (did retrieval get the right chunks?), and answer relevancy. 20 golden test cases with known-good answers. run in CI on every prompt change.

          

        

        
rule: Pydantic is your minimum eval. RAGAS is your baseline. LLM-as-judge is your ceiling. ship none of these and you're flying blind.

05 — quick reference

  
engineer's cheatsheet

  
the things you forget and google at 2am.


  


    

      
[ RAG pipeline ]

      
1. loadparse with Docling (not pypdf). preserve structure.

      
2. chunkrecursive, 512 tokens, 50 overlap. semantic > fixed for complex docs.

      
3. embedtext-embedding-3-small (fast) or bge-large (quality).

      
4. storeChromaDB (local), pgvector (prod), Qdrant (scale).

      
5. retrievehybrid: BM25 + semantic + reranker = best results.

      
6. generateinject context, instruct no hallucination. stream it.

      
7. evalRAGAS: faithfulness + ctx_precision + answer_relevancy.

    


    

      
[ LangGraph patterns ]

      
StateGraphdefine state schema with TypedDict or Pydantic.

      
add_nodeeach node is a function: state → updated state.

      
add_edgedeterministic. add_conditional_edges for dynamic routing.

      
HITLinterrupt_before=["node"] + checkpointer.

      
memoryMemorySaver in-memory, SqliteSaver persistent.

      
streaminggraph.astream_events() for token-level SSE in FastAPI.

    


    

      
[ prompt engineering ]

      
systemrole + context + constraints + output format. be explicit.

      
CoT"think step by step" or <thinking> for complex reasoning.

      
XML (Claude)wrap context in <context>, docs in <document>.

      
few-shot3–5 examples beats zero-shot for structured output.

      
structuredPydantic + .with_structured_output() = reliable JSON.

      
temperature0 for extraction/SQL/code. 0.7+ for creative outputs.

    


    

      
[ model selection · sep 2026 ]

      
reasoningClaude Opus 5.5 / Fable 5.1 / GPT-6 Astra. complex analysis.

      
daily driverClaude Sonnet 5.5 / GPT-6 Sol. docs, agents, tool use.

      
fast + cheapClaude Haiku 4.5 / GPT-6 Luna / Gemini 3.5 Flash-Lite.

      
decisionsJev for routing, gating, labeling. typed + calibrated.

      
open weightsDeepSeek V4 Flash, GLM-5.2 (code), Qwen 3.8 (local).

      
voiceGemini 3.8 Live / OpenAI Realtime.

    


    

      
[ evals checklist ]

      
faithfulnessanswer grounded in retrieved context? (RAGAS)

      
ctx_precisionretrieved chunks actually relevant? (RAGAS)

      
answer_relanswer addresses the question? (RAGAS)

      
hallucinationLLM-as-judge: claim unsupported by context?

      
latencyp50/p95/p99. budget: <2s simple, <8s agentic.

      
costtrack tokens per request. cache aggressively.

    


    

      
[ deployment ]

      
Railwaypush to github → auto-deploy. free tier. what I use.

      
Dockerpin base image. slim variants. multi-stage builds.

      
env varsnever hardcode keys. .env local, secrets in prod.

      
cachingsemantic cache with Redis. huge cost saver.

      
rate limitsexponential backoff + jitter. tenacity in Python.

      
monitoringLangSmith traces. Sentry errors. log everything.
